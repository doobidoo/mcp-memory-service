- **A second oversized edit no longer leaves the chunks of the first one in the store (#2143).**
  On a backend without `update_memory_versioned`, an edit larger than `max_content_length`
  goes through `_store_unversioned_split_replacement()`, which only ever deleted the row the
  edit was addressed to. When that row came back as chunk 0, the other chunks of the previous
  edit stayed live, under an `original_hash` naming text that no longer exists. A split edit
  now marks the chunks it writes with the hash the memory keeps across edits and lists them on
  its first chunk, so the next edit reuses the ones it still needs and deletes the rest after
  writing its own. Rows written before this change carry no marker and are left alone: they
  are only reachable through their salted hash and there is no safe way to tell them from a
  chunk another memory shares.
